# Deterministic Dual-Channel Thruster System Design

**Date:** 2026-08-02  
**Project:** Shattered Orbit  
**Branch:** `agent/playable-flight-room`

## 1. Purpose

Replace the current combined force/torque visual allocator with a deterministic, testable thruster system for the canonical Small Sci-Fi Fighter.

The new system must satisfy all of the following:

- Direct exhaust appears only while the player is actively commanding acceleration or rotation.
- Retained velocity never activates direct exhaust.
- Assisted damping, drift correction, auto-bank, and stabilization remain visible, but dimmer than direct pilot thrust.
- Every movement action activates only approved thrusters.
- Every selected thruster must contribute force or torque in the correct direction.
- Source-exact Blender exhaust geometry remains the visual source of truth.
- Plumes grow and shrink smoothly while remaining anchored to the real nozzle pivot.
- The system fails closed when the imported hierarchy, geometry, or action mapping is invalid.

This is a dedicated fighter-thruster phase. It does not expand into a generalized multi-ship propulsion framework.

## 2. Current Problems

The current visual controller solves one combined force/torque request through a generic allocator. This causes several failures:

- Pilot input and automatic assistance are mixed together.
- Coasting and corrective forces can be visually confused.
- Wrong thrusters may activate for a requested direction.
- Some actions may not visibly activate any thruster.
- Visual debugging requires flying and guessing instead of inspecting deterministic action outputs.
- The current schema-3 effect meshes are stored in ship space, so scaling them would move them away from the nozzle because the pivot is the ship origin.
- Godot hierarchy resolution currently assumes too much about imported wrapper depth.
- Up/Down input tests still contain stale expectations after the approved control swap.

## 3. Selected Architecture

The system uses two independent visual channels.

### 3.1 Direct pilot channel

The direct channel is driven only by the current `FlightCommand`.

It receives:

- translation input;
- rotation input;
- boost input.

It does not receive velocity, damping force, stabilization torque, or auto-bank corrections.

Examples:

- No input while coasting at any speed: no direct exhaust.
- Forward held: main thrusters active.
- Reverse held: retro thrusters active.
- Strafe, pitch, yaw, and roll input: only the approved maneuvering thrusters activate.

### 3.2 Assisted correction channel

The assisted channel is driven by automatic corrections generated by assisted flight mode:

- lateral and vertical drift damping;
- angular damping;
- coordinated auto-bank;
- other explicit stabilization contributions already produced by the flight model.

The assisted mapper produces normalized raw intensities in the range `0.0..1.0`. Before merging with direct output, each assisted intensity is scaled once by `0.35`.

Assisted output is therefore visually subordinate:

- maximum final assisted contribution: `35%`;
- lower emission than direct output;
- no boost amplification;
- no direct-input color or brightness dominance.

When direct and assisted channels request the same thruster:

```text
final_target = max(direct_intensity, raw_assisted_intensity * 0.35)
```

The `0.35` multiplier is applied exactly once. The channels do not add together beyond full intensity.

## 4. Flight Telemetry Split

`FlightOutput` will expose separate contributions:

```text
pilot_force_local
pilot_torque_local
assist_force_local
assist_torque_local
```

Applied physics remains:

```text
total_force_local  = pilot_force_local  + assist_force_local
total_torque_local = pilot_torque_local + assist_torque_local
```

The visual system receives the split contributions rather than only the totals.

Velocity remains an input to assisted physics calculations, but it is never a direct input to the visual controller.

## 5. Deterministic Action Mapping

The system uses a capability-validated action matrix instead of a free-form allocator.

Each thruster has:

```text
position
reaction_force_direction
produced_torque = position × reaction_force_direction
```

The action matrix covers:

- forward;
- reverse;
- strafe left;
- strafe right;
- strafe up;
- strafe down;
- pitch up;
- pitch down;
- yaw left;
- yaw right;
- roll left;
- roll right.

Each action maps to an explicit approved set of thrusters and per-thruster weights.

### 5.1 Mapping lifecycle

The mapping is not recomputed during gameplay.

1. Schema-4 exporter data defines each thruster's verified position, force direction, torque contribution, and semantic path.
2. A development-time capability validator evaluates candidate action mappings.
3. Calibration mode displays the candidate mappings and their force/torque contributions.
4. The approved action matrix is written as deterministic checked-in project data.
5. Runtime reads only that fixed checked-in matrix.
6. Tests verify that the checked-in matrix remains compatible with the current schema-4 manifest.

A changed fighter manifest or changed thruster capability invalidates the checked-in mapping until it is deliberately recalibrated and recommitted.

### 5.2 Mechanical validation

The mapping is validated before runtime visuals are enabled:

- Selected translational thrusters must contribute force with the requested sign.
- Selected rotational thrusters must contribute torque with the requested sign.
- Contributions in opposing directions must remain below defined tolerances.
- Every action must have a non-empty valid mapping.
- Opposite actions must produce opposite force or torque signs.
- Every installed maneuvering thruster must participate in at least one physically valid action.
- Invalid entries report the exact action and thruster path and disable all visual output.

Direct pilot input uses this deterministic matrix.

Assisted force and torque use the same checked-in capability mapping, but are driven by the separate correction telemetry and capped to a `35%` visual contribution.

## 6. Schema-4 Nozzle-Local Geometry

The source-exact schema-3 meshes preserve the correct full-size geometry, but their node pivots are not suitable for safe growth animation.

Schema 4 converts each effect into nozzle-local coordinates.

For each thruster effect, Blender will:

1. Read the exact evaluated source vertices and faces from the original `EngineFire*` object and its assigned physical plume group.
2. Use the verified nozzle position and exhaust basis as the effect node transform.
3. Convert canonical ship-space vertices into nozzle-local coordinates.
4. Export the effect node at the nozzle transform.
5. Record the source component indices, geometry digest, local bounds, nozzle transform, and reconstruction error.
6. Verify that reconstructing every exported local vertex returns the original canonical source vertex within tolerance.

Required reconstruction property:

```text
effect_transform * local_vertex ≈ canonical_source_vertex
```

The export fails if the maximum reconstruction error exceeds the contract tolerance.

At full scale, the runtime mesh must be geometrically identical to the authored Blender plume. During growth and decay, the nozzle end remains fixed.

## 7. Growth and Decay Envelope

The system uses a symmetric smootherstep envelope rather than a simple exponential interpolation.

The target intensity is converted into a temporal state with these default response times:

```text
direct rise:  0.22 seconds
direct fall:  0.22 seconds
assist rise:  0.16 seconds
assist fall:  0.16 seconds
```

The envelope is monotonic in both directions.

For envelope value `e`:

```text
s = smootherstep(e)
length scale = lerp(0.04, 1.00, s)
radius scale = lerp(0.22, 1.00, s)
opacity      = e²
emission     = e³
```

This produces:

```text
tiny spark → small plume → large plume → full authored plume
```

Release performs the exact reverse progression.

At zero:

- the mesh is hidden;
- alpha is zero;
- emission is zero;
- envelope state is reset to zero;
- retained velocity does not reactivate the direct channel.

Boost may increase emission and apply a small length multiplier only to already-active main or retro effects. Boost cannot activate an idle effect.

## 8. Imported Hierarchy Resolution

Godot must resolve the logical `Thrusters` and `ThrusterEffects` roots independently of imported wrapper depth.

Runtime requirements:

- exactly one logical `Thrusters` hierarchy;
- exactly one logical `ThrusterEffects` hierarchy;
- twelve unique semantic socket paths;
- twelve unique semantic effect paths;
- one socket/effect pair per thruster;
- no missing, duplicated, or renamed semantic path;
- all required meshes loaded before visual output is enabled.

Hierarchy discovery must inspect the actual imported subtree and must not assume that either logical root is a direct child of the packed-scene instance.

Any hierarchy failure disables all thruster visuals and reports the exact violated condition.

## 9. Calibration Mode

A development-only calibration scene will trigger one action at a time.

Supported actions:

- forward;
- reverse;
- strafe left/right;
- strafe up/down;
- pitch up/down;
- yaw left/right;
- roll left/right;
- assisted translation correction;
- assisted rotation correction.

For the selected action, calibration mode displays:

- requested pilot force and torque;
- requested assisted force and torque;
- active thruster semantic paths;
- per-thruster force contribution;
- per-thruster torque contribution;
- direct intensity;
- raw assisted intensity;
- capped assisted contribution;
- final merged target;
- current envelope state.

Calibration mode does not modify production mappings during ordinary execution. Deliberate recalibration produces a reviewed mapping file that must be committed like any other source change.

## 10. Input Contract

The approved arrow-control mapping is:

```text
Down Arrow → pitch up
Up Arrow   → pitch down
```

All input and integration tests must use this mapping. Stale tests expecting the opposite behavior must be corrected during this phase.

## 11. Failure Handling

The system fails closed.

Visuals remain disabled when any of these occur:

- schema version mismatch;
- missing or duplicate hierarchy root;
- missing socket or effect path;
- invalid nozzle transform;
- geometry reconstruction error above tolerance;
- checked-in mapping does not match the current manifest;
- invalid force or torque sign in the action matrix;
- an action has no valid thruster set;
- a thruster effect has no valid source geometry;
- direct and assisted telemetry is unavailable.

Errors must identify the exact path, action, mapping record, or contract field that failed.

The exporter remains transactional: pending GLB and manifest files replace live assets only after schema validation succeeds.

## 12. Testing Strategy

### 12.1 Pure logic tests

- Direct channel remains zero with zero command at any velocity.
- Assisted channel responds only to explicit correction contributions.
- Raw assisted intensity remains normalized to `0.0..1.0`.
- The assisted multiplier is applied exactly once.
- Final assisted contribution never exceeds `35%` when direct output is zero.
- Every action activates exactly its approved checked-in thruster set.
- Selected thrusters contribute the correct force or torque sign.
- Opposite actions produce opposite mappings.
- Every thruster is used by at least one valid capability where physically appropriate.
- Merge uses `max(direct, raw_assist * 0.35)`.
- Boost cannot activate an idle thruster.
- Rise and fall envelopes are monotonic.
- Envelope reaches the intended endpoints.

### 12.2 Exporter and manifest tests

- Schema 4 is required.
- All twelve nozzle-local effect records exist.
- Source component groups remain exact.
- Geometry digests are present and unique where expected.
- Full-size reconstruction returns source-exact canonical vertices within tolerance.
- The checked-in action matrix references the current manifest identity and paths.
- Transactional export never publishes an invalid asset.

### 12.3 Godot integration tests

- Imported hierarchy resolves after clean reimport.
- Twelve socket/effect pairs resolve uniquely.
- No effect is visible at idle.
- Direct input activates expected effect paths.
- Coasting does not activate direct effects.
- Assisted corrections activate dimmer effects.
- Effect transforms retain nozzle anchoring through envelope changes.
- Up/Down tests match the approved controls.

### 12.4 Manual calibration gate

Each supported action is triggered independently in calibration mode and visually checked against reported force and torque contributions.

## 13. Acceptance Criteria

The dedicated thruster phase is complete only when all conditions below are satisfied:

1. Python geometry, mapping, and exporter tests pass.
2. Blender schema-4 export passes.
3. The schema-4 contract validates all twelve nozzle-local source-exact meshes.
4. The checked-in deterministic action matrix validates against the schema-4 manifest.
5. Godot headless import passes.
6. Every registered unit and integration suite passes.
7. Calibration mode validates all twelve movement actions plus assisted correction cases.
8. Manual flight confirms:
   - no direct exhaust while coasting;
   - direct exhaust follows held input;
   - assisted correction exhaust is visibly dimmer;
   - every movement direction uses the physically correct thrusters;
   - all expected thrusters activate;
   - growth and decay remain nozzle-anchored;
   - boost modifies only active main or retro effects.

After this acceptance gate, development returns to the existing Shattered Orbit master roadmap. Asteroid overlap cleanup remains deferred to the environment-composition phase.

## 14. Explicit Non-Goals

This phase does not include:

- generalized support for arbitrary future ships;
- damage, destruction, or disabled thruster states;
- fuel simulation;
- heat distortion shaders;
- particle trails;
- asteroid placement refinement;
- unrelated flight-model tuning;
- weapon or combat systems.
